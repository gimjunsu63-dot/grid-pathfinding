# 격자 지도 최단 경로 탐색 비교 (BFS · 다익스트라 · A*)

[![test](https://github.com/gimjunsu63-dot/grid-pathfinding/actions/workflows/test.yml/badge.svg)](https://github.com/gimjunsu63-dot/grid-pathfinding/actions/workflows/test.yml)

2026-2 고급알고리즘 개인프로젝트 · 2026193209 김준수

장애물이 있는 2차원 격자 지도에서 출발 칸부터 도착 칸까지 비용이 가장 작은 경로를 찾는
세 방식(BFS, 다익스트라, A*)을 같은 조건에서 구현하고 비교합니다.

- 저장소는 [`algorithm-env`](https://github.com/lec-algorithm/algorithm-env) 템플릿으로 만들었습니다.
- Python 표준 모듈만 씁니다 (외부 라이브러리 없음).

## 실행 방법

Codespaces나 `docker compose exec lab bash`로 컨테이너에 들어간 뒤:

```sh
make test          # 유닛 테스트
make run           # 작은 예제 지도 3개에서 세 알고리즘 실행
make maps          # 지도 종류별 작은 샘플 출력
make bench         # 실험 전체 실행 -> results/*.csv (수 분)
make bench-quick   # 실험 전체를 아주 작은 지도로 빠르게 (동작 확인용)
make figures       # 지도별로 세 알고리즘이 탐색한 칸과 경로를 그림으로 -> figures/maps/
make analyze       # results/*.csv로 그래프와 표 만들기 -> figures/charts/, figures/RESULTS.md
make results       # bench + analyze + figures 한 번에 (약 5분)
```

**결과 보기**: [`figures/RESULTS.md`](figures/RESULTS.md) (그래프와 표), [`figures/README.md`](figures/README.md) (지도별 탐색 범위 그림)

실험 하나만 다시 돌릴 때:

```sh
python3 src/bench.py --exp A          # 실험 A만 (그다음 make analyze)
python3 src/bench.py --exp C D        # 실험 C, D만
python3 src/bench.py --maps 3 --repeats 2   # 지도 수, 반복 수 바꾸기
```

컨테이너 없이도 Python 3.11 이상이면 같은 명령으로 돌아갑니다.

## 구현 규칙

비교가 공정하도록 세 알고리즘이 다음을 똑같이 따릅니다.

| 항목 | 규칙 |
| --- | --- |
| 입력 | `(grid, start, goal)`, 위치는 `(행, 열)` |
| 출력 | `SearchResult(path, cost, expanded, stale, max_frontier)` |
| 이동 | 상하좌우 4방향, 이웃 칸 순서 고정 (위, 아래, 왼쪽, 오른쪽) |
| 비용 | 들어가는 칸의 비용을 더함 (출발 칸 비용은 안 냄), 장애물은 0 |
| 종료 | 도착 칸을 큐/힙에서 **꺼낼 때** 종료 |
| 다익스트라 | A*에서 h = 0인 경우. 코드 하나(`best_first`)를 같이 씀 |
| A* 휴리스틱 | 맨해튼 거리. 칸 비용이 1 이상이라 실제 비용보다 크지 않으므로 최적 보장 |
| A* 동점 처리 | 기본은 f가 같으면 g가 큰 칸 먼저 (`tie_break` 인자로 바꿀 수 있음) |

측정값 정의:

| 이름 | 뜻 |
| --- | --- |
| `expanded` | 큐/힙에서 꺼내서 처리한 칸 수 (이미 확정된 칸의 낡은 항목은 제외) |
| `stale` | 꺼냈지만 낡은 항목이라 버린 수. `heapq`에 값 갱신 기능이 없어 같은 칸을 여러 번 넣기 때문 (BFS는 항상 0) |
| `max_frontier` | 탐색 중 큐/힙 크기의 최댓값 (낡은 항목 포함, 실제로 차지한 메모리 기준) |

## 지도

모든 지도는 시드가 같으면 항상 똑같이 만들어집니다. 장애물과 칸 비용은 서로 다른 난수열에서
뽑기 때문에, 시드가 같으면 비용 1 지도와 비용 1~9 지도의 장애물 배치가 완전히 같습니다.

| 종류 | 설명 | 출발 → 도착 |
| --- | --- | --- |
| `random` | 칸마다 `wall_ratio` 확률로 장애물 | 왼쪽 위 → 오른쪽 아래 |
| `maze` | 재귀 백트래킹 미로 (스택으로 구현해서 재귀 한도 없음). `loop_ratio`로 벽을 더 뚫어 순환 경로 추가 | 왼쪽 위 → 오른쪽 아래 미로 칸 |
| `nopath` | 연결된 랜덤 지도에서 도착 칸을 벽으로 막음. 세 알고리즘 모두 도달 가능한 칸을 전부 탐색해야 하는 최악의 경우 | 왼쪽 위 → 오른쪽 아래 |
| `uwall` | 빈 지도에 출발 쪽으로 입구가 열린 U자 벽. A*가 휴리스틱을 따라 U자 안으로 들어갔다가 돌아 나오는 함정 | 왼쪽 가운데 → 오른쪽 가운데 |
| `terrain` | 비용 1~9가 덩어리로 모여 있는 지형 (value noise). 장애물 없음 | 왼쪽 위 → 오른쪽 아래 |
| `city` | 건물 블록 사이 도로망. 간선도로 1, 일반 도로 3, 정체 구간 9, 도로 일부 통제(벽) | 왼쪽 위 → 오른쪽 아래 |

**연결 규칙**: `random`과 `city`는 출발과 도착이 이어지지 않으면 같은 시드의 다음 난수로
지도를 다시 뽑고, 몇 번 만에 뽑혔는지(`attempts`)를 CSV에 기록합니다.

**랜덤 출발·도착**: 출발 칸과 같은 연결 영역 안에서 두 칸을 무작위로 고르되, 맨해튼 거리가
(가로 + 세로) / 4 이상인 쌍만 씁니다.

## 실험

기준 조건은 **크기 200 × 200, 랜덤 장애물 20%, 비용 1, 모서리 출발·도착**이고,
실험마다 이 중 하나만 바꿉니다.

| 실험 | 바꾸는 것 | 조건 |
| --- | --- | --- |
| A | 지도 크기 | 50, 100, 200, 400 |
| B | 장애물 비율 | 0, 10, 20, 30% |
| C | 지도 종류 | 랜덤, 미로, 순환 미로, 경로 없음, U자 벽, 도시(비용 1) |
| D | 비용 | 랜덤·도시 지도 비용 1 vs 비용 다름, 지형 |
| E | 출발·도착 | 모서리 고정 vs 랜덤 (비용 1, 비용 1~9) |
| T | A* 동점 처리 | f가 같을 때 g 큰 칸 먼저 / g 작은 칸 먼저 / 넣은 순서 |
| W | 가중치 A* | h에 1, 1.5, 2, 3, 5를 곱함 (다익스트라와 비교) |
| H | 우선순위 큐 | `heapq`(C로 구현) vs 파이썬으로 짠 이진 힙, 같은 탐색 코드 |
| BI | 양방향 탐색 | 다익스트라, A*, 양방향 다익스트라 (모서리 / 랜덤 출발·도착, 지도 종류별) |
| noise | 측정 흔들림 | 같은 지도를 30번씩 반복해 시간이 얼마나 흔들리는지 |

A~E와 noise는 BFS · 다익스트라 · A* 세 가지를, T · W · H · BI는 표에 적은 알고리즘들을 비교합니다.

측정 규칙:

- 조건마다 지도 10개(시드 2026~2035) × 지도마다 5번 반복
- 반복할 때마다 알고리즘 실행 순서를 돌림 (항상 같은 알고리즘이 먼저 돌지 않게)
- 탐색 함수 호출만 시간을 잼 (`time.perf_counter_ns`). 지도 생성과 기준값 계산은 제외
- 시간을 재는 동안 가비지 컬렉터를 멈춤
- 매 실행마다 결과를 검사: 다익스트라, A*, 양방향 다익스트라는 최적 비용이어야 하고,
  BFS는 최적보다 작을 수 없고, 가중치 w인 A*는 최적의 w배를 넘을 수 없음. 어긋나면 실험이 에러로 멈춤

결과 CSV의 한 줄은 "지도 하나에서 알고리즘 하나를 한 번 실행한 결과"이고, 같이 저장되는 기준값은
열린 칸 수(`open_cells`), 출발에서 도달 가능한 칸 수(`reachable`), 맨해튼 거리(`manhattan`),
최적 비용(`optimal_cost`)입니다. 실행한 컴퓨터, Python 버전, 커밋은 `results/<실험>.env.json`에 남습니다.

## 분석

`make analyze`가 `results/*.csv` 원본에서 다시 계산해서 그래프와 표를 만듭니다. 쓰는 지표:

| 지표 | 계산 |
| --- | --- |
| 시간 | 지도 10개 × 5번 실행의 중앙값, 사분위 범위(IQR) 함께 |
| 기울기 | 로그-로그 그래프에서 칸 수에 대한 기울기 (1이면 칸 수에 비례) |
| 칸당 시간 | 시간 ÷ 탐색한 칸 수 (마이크로초) |
| 탐색 비율 | 탐색한 칸 ÷ 출발에서 도달 가능한 칸 |
| 휴리스틱 정확도 | 출발점의 맨해튼 거리 ÷ 최적 비용 |
| A* 작업 비율 | 같은 지도에서 A* 탐색 칸 ÷ 다익스트라 탐색 칸 |
| 비용 비율 | 찾은 경로 비용 ÷ 최적 비용 |
| 코드 줄 수 | 함수별 줄 수 (빈 줄, 주석, 독스트링 제외) |

알고리즘별 색은 모든 그림에서 같습니다: BFS 파랑, 다익스트라 청록, A* 주황, 양방향 보라.

## 탐색 범위 그림

`make figures`를 실행하면 지도 종류마다 BFS · 다익스트라 · A*가 탐색한 칸과 찾은 경로를
나란히 그린 PNG가 `figures/maps/`에 생기고, 한눈에 보는 페이지 [`figures/README.md`](figures/README.md)가 만들어집니다.

탐색한 칸은 알고리즘 코드를 고치지 않고 기록합니다. 세 알고리즘 모두 칸 하나를 처리할 때
`grid.neighbors()`를 정확히 한 번 부르기 때문에, 이 호출을 기록하는 격자(`RecordingGrid`)를 넘기면
실제 코드가 실제 순서대로 탐색한 칸이 남습니다. 기록한 칸 수가 알고리즘이 보고한 `expanded`와
같은지도 테스트로 확인합니다.

## 테스트

`make test`가 확인하는 것:

1. 손으로 답을 아는 작은 지도 (막힌 길, 출발=도착, 출발/도착이 벽, 경로 없음, 비용 때문에 BFS가 틀리는 지도)
2. 랜덤 지도 300개에서 다익스트라·A* 비용을 **별도로 짠 참조 구현**(단순 반복 완화)과 비교
3. 랜덤 지도에서 세 알고리즘끼리 일치하는지
4. 지도 생성: 같은 시드면 같은 지도, 출발·도착은 항상 열린 칸, 연결 여부, 완전 미로는 트리 구조,
   큰 미로(401 × 401)에서도 재귀 에러 없음, U자 벽이 직선 경로를 막는지, 지형 비용이 실제로 뭉쳐 있는지
5. 측정 코드: 작은 실험을 돌려서 CSV 줄 수, 최적 비용 검사, 실행 순서 교대가 맞는지
6. 그림 코드: 기록한 탐색 칸 수 = `expanded`, 기록해도 결과가 같은지, PNG 파일 형식이 맞는지
7. 추가 알고리즘: 직접 짠 힙이 `heapq`와 같은 순서로 꺼내는지, 어느 힙을 써도 탐색 결과가 똑같은지,
   양방향 다익스트라를 참조 구현과 랜덤 지도 300개에서 비교, 가중치 A* 비용이 최적의 w배 이내인지
8. 분석 코드: 작은 실험 전체로 그래프·표를 끝까지 만들어 보고, SVG 형식이 맞는지
